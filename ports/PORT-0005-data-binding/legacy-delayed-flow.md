## Legacy GenroPy: distinct scheduling mechanisms

1. `genro.callAfter(cb, timeout, scope, reason)` converts the callback with `funcCreate`, defaults scope to `genro`, and uses `dojo.hitch(scope,cb)`. A truthy `reason` indexes global `pendingCallAfter`: an earlier timer with the same key is cleared and replaced. Without reason, calls are independent. The map entry is assigned a timer handle and is not deleted when the callback fires in the inspected function (`gnrjs/gnr_d11/js/genro.js:1186-1198`; map allocation at `:194`). A zero/falsy reason takes the unkeyed path. This is a global keyed debounce, not Source-node ownership.
2. `genro.fireAfter(path,msg,timeout)` uses the **same** `pendingCallAfter` map, keyed by path; replaces a pending timer at that path; callback calls `genro.fireEvent(path,msg)`. `timeout || 1` makes zero become 1 ms. A `callAfter` whose reason equals this path and a `fireAfter` can therefore replace one another. The entry is likewise not deleted on firing (`genro.js:1200-1210`). `setDataAfter` is separate: unkeyed timer that eventually calls `genro.setData`; no cancellation handle is kept here (`:1211-1215`). No disposal/cancellation contract for these global timers was found in the inspected functions.
3. Legacy Source-node `delayedCall(cb,delay,code)` uses a field `_dc_` plus `code` (default `delayedCall`) on the node, clears only the earlier handle for that same code, then sets a timer. `delay || 1` changes zero to 1 ms; callback is passed directly to `setTimeout`, so this helper does **not** bind `this` or inject arguments (`gnrjs/gnr_d11/js/gnrdomsource.js:1150-1158`). This is separate from `genro.callAfter` and provider `_delay`.
4. For `dataFormula`, `dataController`, `dataScript`, `dataRpc` and other providers, Source-node `setDataNodeValue()` reads `currentAttributes()._delay`. Literal `'auto'` disables the delay in current code. A truthy delay clears `this.pendingFire` and schedules `setDataNodeValueDo` on the **same node**, bound by `dojo.hitch`; the scheduled arguments are the latest trigger's `nodeOrRunKwargs`, Bag event `kw`, trigger relationship and subscription args (`gnrdomsource.js:218-265`). The timer handle is not cleared/reset after firing in that function. This debounces each provider node separately; it does not use `pendingCallAfter` or `_dc_*`.
5. Legacy Python `dataFormula(path,formula,**kwargs)` and `dataController(script=None,**kwargs)` author Source nodes with `path/formula` and `script` respectively (`sourcerer_clones/genropy/genropy/gnrpy/gnr/web/gnrwebstruct.py:1345-1369`). `_onStart` numeric is copied to `_delay` only when no delay exists; `_onBuilt` numeric creates an independent `setTimeout` that calls `node.setDataNodeValue()` later (`gnrjs/gnr_d11/js/genro_src.js:683-700`). `setTiming` is an interval mechanism, distinct from debounce, with interval cleanup on deletion (`gnrdomsource.js:1687-1694,1040-1060`).

## Legacy provider execution after the timer

- `setDataNodeValueDo` executes when scheduled. It rereads `this.attr`, removes control fields including `_delay`, computes destination via `absDatapath`, and resolves each binding from the **current** Data through `getAttributeFromDatasource` (`gnrdomsource.js:267-310,326-374`). Thus the latest trigger object is captured while bound input values are sampled again at execution. `kw.reason=='autocreate'` and `_userChanges` can veto execution at this point (`:280-285`). `_ask` handling is in the immediate branch only after the `_delay` branch; a truthy delay bypasses that prompt in the inspected control flow (`:227-263`); whether intended is open.
- Controller/formula callback context is the Source node (`f.apply(this,...)`). The leading arguments are `_kwargs` (map of sampled bindings), `_node` (triggering Bag node when applicable), `_triggerpars` (`{kw,trigger_reason}`), `_reason`, then subscription arguments and each declared binding. Formula prepends `return` to expression; controller uses `script`; a result `path` writes with `setRelativeData` (`gnrdomsource.js:306-310,326-374,376-489`). The callback can see the latest event's reason but currently sampled bindings. Legacy behavior includes `_if/_else`, `_ask`, subscriptions, RPC and other branches; these are adjacent, not implied by a delayed formula/controller slice.
- `trigger_data` classifies node/container/child relationships and dispatches provider execution (`gnrdomsource.js:129-181`). Source construction wires `_onStart`, `_onBuilt`, timing and subscriptions (`genro_src.js:650-703`). Formula and controller scheduling is therefore downstream of Data events and startup, not an independent global event queue.
- Legacy deletion path calls `_onDeleting` and `cleanupNodeSubscriptions` (`genro_src.js:347-403`). `_onDeleting` clears intervals, shortcuts and watches (`gnrdomsource.js:1040-1061`), but no clear of `pendingFire` or `_dc_*` is visible there or in `destroy()` (`:112-127`). This is a **reviewed lifecycle gap**, not proof no indirect cleanup exists elsewhere. An already scheduled callback retains a bound Source node; cancellation on deletion is not established by these paths.

## PoC comparison

- PoC `SourceBagNode.delayedCall(callback,delay,code)` tracks handles in a per-node Map, replaces only the same code, deletes the entry upon firing, invokes callback with `this=node`, validates finite nonnegative milliseconds and checks builder disposal. `cancelDelayedCalls()` clears all node timers and resets pending/click state (`js/dom/src/source-bag.js:51-73`). These are stronger lifecycle rules than the inspected legacy helper. Provider delay uses reserved key `'provider'` and `pendingFire`; `LogicRuntime.compute()` applies it to non-setter nodes, treating null/false/zero/`'auto'` as immediate. The callback enters `application.live` and calls `computeNow(node,trigger,extra)` (`js/dom/src/logic/runtime.js:161-179`). Unlike legacy, invalid delay values raise in `delayedCall`.
- PoC `computeNow` rereads node attributes and calls `builder._bindings(node)` at execution, so formula/controller inputs are fresh. Formula gets a bindings map and writes destination; controller gets Source node plus bindings, `sourceNode`, `gramlot`, `_triggerpars` and `_reason` (`js/dom/src/logic/runtime.js:136-151,181-213`). This is similar in effect to legacy fresh binding reads, but callback signature and execution vocabulary differ. `DATA_ELEMENT_FIELDS` filters `_delay` from binding inputs (`:6-12`; `js/dom/src/builder-base.js:429-446`). PoC has startup dependency ordering for formulas, then controllers/RPC (`js/dom/src/logic/runtime.js:92-124`). Reactive formula queue inside `live` is deduped and drained separately from millisecond `_delay`; controllers run synchronously before delayed timer unless `_delay` is set (`js/dom/src/builder-handler.js:280-333`).
- On Source removal, PoC `_unregisterPointer` cancels node timers and pending formula queue entries recursively (`js/dom/src/builder-handler.js:197-214`); builder dispose cancels current Source node timers (`js/dom/src/builder-base.js:661-667`). `LogicRuntime.disposeNode` unregisters pointers and cancels remote services (`js/dom/src/logic/runtime.js:235-243`). `js/dom/tests/provider-actions.test.js:15-39` checks coalescing for formula/controller/RPC; `:132-145` checks removal/disposal cancellation for RPC and button timers. `js/dom/tests/local-logic.test.js` and `branch-preparation.test.js` cover reactive/startup formula graph and removed queued formula. Formula/controller-specific removal of an already pending `_delay` timer is inferred from shared cancellation code, but no focused test was identified.
- PoC button `_delay` also uses node `delayedCall` with key `'button'`, accumulating `_counter` and latest click event (`js/dom/src/application.js:280-320`; `js/dom/tests/provider-actions.test.js:98-129`). This is adjacent and should not be confused with provider `_delay`. PoC has no `genro.callAfter`/`genro.fireAfter` method names in its inspected core/logic path; node delayedCall is the actual counterpart to review, not a promised public application API.

## Current Gramlot core and installed published Builder

- Core browser `Gramlot` mounts typed Source and renders it, with no Data event subscription or controller runtime in the live renderer (`js/src/gramlot.js:8-18,69-77`; `js/src/renderer/gramlot-renderer.js:14-33`). Python and JS builder `create()` call setup/main but do not execute browser declarations (`src/gramlot/page/builder.py:47-53`; `js/src/builder/gramlot-builder.js:16-17`). Host main/source return Source only (`src/gramlot/server/host.py:119-139`; `js/src/adapters/host.js:80-91`). Consequently Source-authored `dataFormula`/`dataController` and `_delay` have no live Gramlot execution or timer lifecycle today.
- Installed published Builder JS has generic `_bindings`, `computeLogic`, `_computeNode` with synchronous setter/formula/controller calls (`js/node_modules/@jsr/genro__builders/src/builder-base.js:534-574`). Its SourceBagNode has builder/data ownership but no `delayedCall`/`cancelDelayedCalls` methods in the inspected class (`js/node_modules/@jsr/genro__builders/src/source-bag.js:35-70`; search for these names yielded no results). Its formula form uses `func`, unlike PoC `formula` expression (`.../builder-base.js:567-572`; PoC `js/dom/src/logic/runtime.js:193-210`). Neither this generic synchronous primitive nor grammar declarations establish the legacy delayed behavior in Gramlot. Respect constitution §14: report Builder gaps in its owning project; do not silently copy PoC alternatives into Gramlot.

## Decisions/gaps to settle before any port

- Public scope: node-owned delay for formula/controller is included from the outset by the owner; determine whether global `callAfter`/`fireAfter` are required at all. These are different legacy contracts, with different keys and ownership; do not invent aliases.
- For delayed callbacks, state exact key, replacement rule, zero/`'auto'`/invalid-delay handling, latest event metadata versus fresh binding sample, exception handling, nested `live`/freeze timing, and Source removal/disposal cancellation. Decide whether to preserve legacy lifecycle gaps or intentionally improve them.
- Clarify callback API and authoring parity (`path`/`script` vs `destination`/`func` or `formula`), startup timing, relative Data paths and trigger relation. Legacy feature names alone do not approve a new Gramlot API. Confirm ownership between published Builder primitives and Gramlot's future reactive coordinator before code changes.
